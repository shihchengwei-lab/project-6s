# 專案 6S

依使用者指定的範圍整理專案，讓接手者能從現行文件找到正式來源、執行必要操作。

## 確認範圍

- 讀協作規則，依文件用途選定核對版本，交代整理範圍、要維持的行為與驗證方式。
- 有 Python 3.11 以上且儲存庫已有 Git 提交時，用 `python <腳本路徑> <儲存庫根目錄> --base <版本>` 執行[盤點腳本](scripts/inventory.py)。省略 `--base` 時使用掃描開始的提交。保留結果的 `base_commit` 供重跑。變更清單用來定位受影響的引用，失效連結與同內容檔案則直接檢查現有檔案。
- 結果為 `unstable` 時，等工作目錄穩定後重跑。結果為 `partial` 時，補查略過或無法讀取的項目。腳本無法使用時，直接盤點現有檔案與引用。
- 從變更的實作、規格或驗證結果追查現行文件的引用與文字轉述。把受影響內容與核對依據納入整理範圍。同內容檔案依各自用途決定去留。
- 沿用既有建置、測試與資產清單。同類問題先處理並驗證一例，再套用到其餘項目。
- 提交、推送、部署與發布依使用者指示執行。

## 處理舊副本與產物

把相互依賴的檔案與引用當成一批。用途、授權或封存位置待確認時，保留該批資料，繼續其他清理。

1. **先建立復原依據。** 核對程式引用、人工流程、授權、原稿用途與重建方式。在本機留一份可供續作的紀錄，寫明原路徑、正式位置、預定去向、復原來源和要更新的引用。確認原始內容可從既有版本或經授權的隔離備份還原，未提交內容要以實際檔案為準。
2. **準備替代來源。** 讓正式來源可用，再把建置、維護流程與文件的引用指向正式來源，並按選定版本更新文件。搬移或刪除前重新核對來源、引用與安全條件。發現其他變更時，依現況重新判斷。
3. **驗證預定的最終狀態。** 保留復原依據，在舊路徑不可用的狀態下走[收尾驗證](#驗證與收尾)。失敗時，復原受影響的路徑和引用，或留下實際去向與待驗項目供續作。中斷後，先核對原路徑、正式位置、備份與引用，再決定復原或續驗。還原前辨認並保護期間的其他編輯。
4. **定案。** 驗證通過後，重新核對操作對象、授權與本批是否有後續改動，再永久移除已確認無用的舊檔。需保存時，優先封存於工作區外或既有獨立封存服務。核對內容與存取權，封存位於專案內時加驗日常搜尋與模型讀取的隔離。確認封存可用後才移除來源，再清除僅供本次復原的資料。

## 六項 6S 檢查表

依本次範圍核對相關項目。

| 項目 | 檢查問題 |
|---|---|
| 整理 | 無用的中間檔、過期副本與落選素材已處理？ |
| 整頓 | 每項資訊都有固定位置與單一維護來源？ |
| 清掃 | 失效引用與重複設定已修正？測試涵蓋要維持的行為？ |
| 清潔 | 文件已合併重複內容、改寫過期段落、移除完成的待辦，並保留仍有效的操作、設計、限制與決策理由？ |
| 素養 | 已沿用現有檢查？新增的規則能防止已辨認的問題復發？ |
| 安全 | 核對絕對路徑、專案邊界、符號連結目的地、保存規則與當次授權。保護授權文件、正式來源、使用者資料與無關的未提交變更。 |

涉及測試整理時，讀 [測試 6S](references/test-cleanup.md)。

## 驗證與收尾

- 逐份對照同版來源。完整案例要符合結果，摘要與翻譯要保留會改變判斷的條件。修正差異，列出仍待查證的項目，再照現行文件跑一項同版的代表操作。
- 跑受影響的建置與測試，沿用既有通過條件。需要重建時，將輸出放在隔離位置。檢查失敗時定位原因，修復本次範圍內的問題。
- 腳本可用時，以首次結果的 `base_commit` 重跑盤點，核對本次處理的路徑與引用。
- 清除本次驗證產生的臨時輸出、腳本與快取。
- 回報實際改動、驗證結果，以及仍會影響使用或接手的問題。需要核對時，附上既有紀錄的位置。
