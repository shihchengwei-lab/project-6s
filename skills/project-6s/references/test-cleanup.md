# 測試 6S

目標是讓每個留下的案例守住有意義的契約，不追求增加或減少測試數。

## 判斷案例用途

- 保留可觀察行為、失敗路徑、輸入邊界、資料相容性、型別拒絕與跨模組整合契約。
- 分清重複與分層：單元測試驗邏輯，整合測試驗接線；兩者檢查同一規則不一定重複。刪除前指出哪個留下的案例承接原契約，或為什麼該斷言根本不是必要契約。
- 可刪除的通常是：重複常數、只測測試 helper、跟著實作逐行重算期望、無需求依據的固定文案，以及脆弱的元件內部子節點檢查。
- 外部格式、歷史連結、種子、序列化資料與公開 API 的精確值可能是相容性契約，不能當作普通硬編碼刪除。
- 不任意刪除看似相同的非法輸入案例；先判斷是否守住不同的解析、編碼或安全邊界。

## 修正假通過與污染

- 名稱必須符合真正測到的事：檢查聲音參數不代表實機聽測；SSR 不代表按鈕點擊、焦點或觸控已驗。
- 檢查空集合／空迴圈、未 await 的非同步斷言、找不到項目時的 -1、模糊布林式斷言，以及測試資料根本未走到宣稱的分支。
- 同函式呼叫兩次得到一樣答案，不一定足以驗證決定性；使用多步序列、獨立實例或真正需要固定的相容性例子。
- 模擬與搜尋要有明確上限、固定輸入與找不到情境時的失敗訊息；優先沿用真實重播或小型明確 fixture，避免每輪重新猜種子。
- 測試 helper 只在確有重複情境時共用；避免萬用 fixture、隱藏副作用及整片無關內容依賴。
- 保持測試隔離，還原 mock、環境變數、時鐘與臨時資源。型別拒絕案例放專案既有型別檢查入口，不當執行期行為測試。

## 驗證修改有效

先跑相關案例，確認故障定位，再執行專案要求的完整檢查。測試數量可變，但須交代移除、合併或補強的理由；不能靠合併成巨型案例美化數字。

重要斷言若有假通過疑慮，可針對該契約作小量反向驗證，例如讓選項集合為空、漏掉已完成分支、讓動畫永不結束。使用隔離副本，或記憶體備份配合 try/finally 還原；確認因預期斷言而失敗，不能把語法或載入失敗當成功抓錯。

反向驗證只證明抽查的契約有效，不代表整套測試無缺口。不為湊覆蓋率新增照抄實作的測試。若發現正式程式缺陷，先留下可重現的失敗與影響，依原任務範圍處理，勿靠修改測試掩蓋。
